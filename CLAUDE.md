# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

jellysync lets peers share Jellyfin libraries without copying files or sharing Jellyfin credentials. One jellysync node runs alongside each peer's Jellyfin. Nodes exchange catalog metadata; for any item a node doesn't have locally but a peer offers, jellysync writes a `.strm` pointer file into the local Jellyfin library. Playing that item streams bytes through the peer's jellysync node on demand — no bulk copying, no shared Jellyfin login. See README.md for the full user-facing explanation, env var reference, and setup flow.

## Commands

Backend (Go, module `jellysync`, root of repo):
```sh
go build ./...              # build
go run ./cmd/jellysync       # run (needs NODE_ID, JELLYFIN_URL, JELLYFIN_API_KEY, OUTPUT_DIR, BASE_URL set)
go test ./...                 # all tests
go test ./internal/strm/...   # single package
go test ./internal/strm/ -run TestPathForEpisode   # single test
go test -race ./internal/e2e/  # end-to-end: whole nodes pairing, syncing and streaming over the mTLS peer port
go vet ./...
```

Frontend (Svelte + Vite + Tailwind, in `web/`):
```sh
cd web && npm install
npm run dev      # vite dev server
npm run build    # builds into internal/webui/static, embedded into the Go binary
```
`internal/webui/static/index.html` as checked into git is just a placeholder so `go build` works without Node installed — the real dashboard only exists after `npm run build` (or the Docker build, which does this automatically, see `Dockerfile`).

Full stack: `docker compose up -d` (see README.md for required env vars in `docker-compose.yml`).

The `VERSION` file at repo root is the node's own version, reported on `GET /health` and, in turn, to any peer that probes it. The Docker build stamps it in via `-ldflags -X main.version=$(cat VERSION)`; a plain `go build`/`go run` leaves it as `"dev"` since that ldflag isn't applied.

## Architecture

Single Go binary (`cmd/jellysync/main.go`, which only loads config and starts the listeners) wiring together `internal/*` packages plus an embedded Svelte dashboard. The wiring itself lives in `internal/app` (`app.New`): stores, sync loop, and the two HTTP surfaces — the **dashboard port** `:8080` (dashboard, its API, and the legacy unauthenticated peer API; never meant to be public) and the **peer port** `:8443` (mutual TLS, see `internal/peerauth`; the only port meant to face the internet). Two env switches gate peer transports, defaulting to pre-mTLS behaviour: `HTTP_PEERS` (default `true`) routes the legacy peer endpoints on `:8080` (`/api/v1/catalog`, `/catalog/changes`, `/catalog/notify`; `stream/{peerID}` always stays, since local Jellyfin playback and the dashboard use it) and allows add-by-URL; `MTLS_PEERS` (default `false`) opens `:8443` and enables invites and redeeming. The peer port is purely additive — if it fails to bind, the node logs an error and keeps serving `:8080`. `PUBLIC_URL` is only needed to create invites. Peers of a switched-off kind are `peers.StateDisabled` (in memory only, never persisted): no heartbeat, skipped by `Sync` and withdrawn at once (items withdrawn, mirror kept), refused by proxy and sync trigger. It's kept out of `main` so `internal/e2e` can run several whole nodes in one test process. No external services besides the node's own local Jellyfin and an embedded SQLite DB (`internal/db`, via `modernc.org/sqlite`, WAL mode).

Main loop, started by `app.Run` (`syncrun.RunLocal`): `catalog.Sync` then `strm.Reconcile`, on the user-configured sync interval (`internal/settings`, default 2h), always in that order in the same cycle — Reconcile reads the table Sync just wrote, so a fresh election is reflected in `.strm` files within the same cycle rather than racing an independent timer. **jellysync never triggers a Jellyfin library scan** (`/Library/Refresh`) — scanning files on disk is Jellyfin's own business, on any node; new/removed `.strm` files appear in Jellyfin whenever it next scans. Three levels: a *local* sync (`trigger/local`) re-reads this node's Jellyfin index (`GET /Items`) into the catalog; a *remote* sync (`trigger/{peerID}`) just pulls peers' cached catalogs and leaves the peer alone; a *remote sync with force* (`?force=true`, the dashboard's "force peer to refresh its catalog" checkbox) first asks that peer's node to run its local sync, waits for it, then pulls. Independently, `?resync=true` (the dashboard's "full resync" checkbox) makes that pull re-download the peer's whole catalog instead of the delta (`catalog.RequestResync`, below).

**internal/jellyfin** — thin client for the node's own local Jellyfin (`ListItems`, `Ping`, `NewDownloadRequest`). Computes each item's `GlobalID()`: first available provider ID (`tmdb:`/`tvdb:`/`imdb:`), falling back to a normalized title+year hash (episodes hash series+season+episode instead, since two different shows can share an episode title). `ListItems` also drops orphans — items whose `Path` isn't under any library in `/Library/VirtualFolders` (Jellyfin keeps such rows when a library is removed while its folder is unreachable); the filter is skipped if the library list can't be fetched. This ID is the cross-node dedup key everywhere downstream. Each item's Jellyfin `Path` travels in `catalog.Entry.Path` (the owner's own filesystem path, shown on the dashboard and used by folder exclusions; empty from older peers).

**internal/catalog** — the sync protocol and election logic.
- `Index` (`index.go`) is this node's own catalog as served to peers: `LocalEntries` (the Jellyfin listing, excluding anything under the `.strm` output dir — jellysync's own generated redirects must never be re-offered as if they were real local media; Jellyfin's `/Items` listing can't tell the two apart, so without this exclusion a node would find its own remote-elected item, mark it local, and delete the `.strm` it just wrote, looping forever) persisted in `local_catalog` as a revisioned change log. `Refresh` diffs a fresh listing against the table and gives every added/changed/removed row the next rev (removals stay as tombstones for 30 days). An `epoch` (random, in `settings`) identifies the history those revs belong to. Peers are served from this table, never from a live Jellyfin listing.
- Peer protocol: `GET /api/v1/catalog/changes?epoch=&since=&limit=` returns one page of changes after rev `since` (`Feed`); an unknown epoch, a cursor older than the tombstone GC watermark, or one ahead of head yields `reset: true` and restarts from 0. `GET /api/v1/catalog` (full list) is kept for pre-feed peers. `POST /api/v1/catalog/notify` is a data-less hint that a peer's catalog changed; it queues a pull-only sync. Responses are gzip-encoded when accepted.
- `pull.go` mirrors each `ONLINE` peer's feed into `peer_catalog`, concurrently across peers, one transaction per page together with the cursor in `peer_sync_state` (resumable). A reset doesn't drop the mirror up front: the resync is written under a new `gen` and older-gen rows are swept only once caught up, so a peer's items never vanish mid-resync. A manual resync (`RequestResync`) sets `peer_sync_state.resync_requested`; `loadCursor` then forgets epoch and rev (keeping `gen`), so the pull goes through the same reset path, and its first page write clears the flag. A 404 on the feed falls back to the legacy full fetch.
- `Sync` = optional `Index.Refresh` → pull peers → elect over `local_catalog` + mirrors of *offering* peers (`peers.Peer.Offering`: ONLINE, or DEGRADED/OFFLINE for less than `peers.WithdrawAfter`, 15 min, since the last successful probe) → write only the rows that differ into `catalog_items`, in one transaction. Dedup rule: local always wins; otherwise the peer with the lexicographically smallest ID among those offering the item is elected primary (a pure function of peer IDs — no latency/timing races between nodes). A peer whose pull failed, or that's briefly unreachable, keeps its last-known mirror in the election, so a missed heartbeat or a peer restart doesn't remove (and Jellyfin re-add as new items) everything it shares. `peer_sync_state.synced_at` is set only when a peer's whole pull succeeds; `catalog.LastSyncTimes` exposes it as `last_sync_at` on `GET /api/v1/peers` (injected into `peers.ListHandler`, since catalog imports peers), shown on the dashboard as "synced N min ago". `syncrun.RunLocal` calls `NotifyPeers` whenever the local refresh found changes; a notified node runs a pull-only sync (no local refresh), so notifications can't ping-pong. `syncrun.Queue` coalesces triggers/notifications into one pending run.
- Hiding (`hidden.go`, `PUT /api/v1/items/hidden`): `hidden_items` holds keys the user excluded from sync — a movie's global_id or a series key (`series_global_id`, else `series_name`; covers the root and every episode). It's only a wish; the next sync applies it. `Index.Refresh` stores a matching local row with `local_catalog.hidden = 1` and a new rev, and the feed serves it as a tombstone (absent from a from-scratch feed and from the legacy full catalog), so peers drop it. The election still counts a hidden local item as local (a peer's copy never replaces it) and keeps a hidden remote item elected; both get `catalog_items.hidden = 1`, and `Reconcile` gives a hidden row no `.strm`. `writeElection` drops any key that no source offers any more (local index, or the mirror of *any* peer, online or not), so a title that vanishes takes its hide with it.
- Folder exclusions (`folders.go`, `GET|PUT /api/v1/peers/{peerID}/excluded-folders`, dashboard port only): `peer_excluded_folders` lists, per peer, folders on *that peer's* filesystem. In `elect`, an offer whose `Entry.Path` is under one (whole-component prefix, case-sensitive, `\` read as `/`) doesn't count; another peer's non-excluded offer wins, and only if none exists is the first excluded offer kept as a row with `catalog_items.hidden_folder = 1` (listed, no `.strm`). Unlike a hide it can't be undone per item — it's recomputed every election. A PUT queues a pull-only sync (reason `settings`). Rows are renamed by `migrateUUIDIDs` and dropped by `pruneRemovedPeers`.
- `status.go`'s `ItemsHandler` (`GET /api/v1/items`) is the dashboard-facing view of `catalog_items`, distinct from the peer-facing wire format in `catalog.go`. `info.go`'s `ItemInfoHandler` (`GET /api/v1/items/info?global_id=`, dashboard port only) adds one item's media details (year, provider IDs) and every copy any source offers (local index and each peer mirror: path, elected, excluded by folder, peer state), backing the dashboard's per-item info modal.

**internal/strm** — turns `catalog_items` rows into `.strm` files under `OUTPUT_DIR/{movies,series}/<peerID>/...` and back. Series roots never get a `.strm` (only episodes are playable). The path's disambiguator suffix (provider ID, or a truncated hash) is load-bearing, not cosmetic — two items can share a display name and would otherwise silently overwrite each other's file. A row's `strm_path` changes only once the file it names is gone: a failed removal (or the old file of a move) stays recorded and is retried next cycle; a move writes the new file before removing the old. Writes are atomic (temp file `.jellysync-*.tmp` + rename). Names are truncated so no path element exceeds 255 bytes. Path updates go in one transaction at the end. Each run ends with a sweep of `movies/` and `series/` deleting any `.strm` (or leftover temp file) no row accounts for — never other files, e.g. artwork Jellyfin saved there. `Reconcile` never asks Jellyfin to rescan.

**internal/peerauth** — authentication on the peer port. Each node has one Ed25519 key (seed in `settings` under `identity_key`, created on first boot); its *pin* (base64url SHA-256 of the SPKI) is its identity. No CA: the server requires a client certificate and `VerifyPeerCertificate` rejects any key that isn't a known client, peer or pending invite, so unknown callers fail the handshake before any HTTP is read; `Authenticate` re-resolves the caller on every request (so a revocation applies to already-open connections) and puts a `Caller` in the context, and `Require*` guards each route by caller kind. Outgoing, `NewTransport` dials a paired peer's `host:port` with mTLS and checks the server key against its pin (any other address — a legacy peer — dials as before, `https://` with CA verification; HTTP/2 is off on purpose, one TCP connection per stream). Pairing is **one-way**: the provider's `POST /api/v1/invites` creates an invite string carrying its URL, its pin and a *temporary* private key whose pin is stored as pending (24h, single-use); the consumer (`peers.RedeemHandler`) uses that temporary key for one mTLS `POST /api/v1/pair` on the provider's peer port, registering its permanent pin as a **client** (`clients` table, `Store`). The provider never dials a client and never adds it as a peer; the consumer adds the provider as an mTLS peer. Mutual sharing is two invites. Clients and peers share one id namespace (`peers.OtherIDs`), and a node that's both gets the same id in both tables, so traffic keys never split.

**internal/peers** — tracks configured peers and their reachability. A peer is either legacy (added by URL or `PEERS`, empty `Pin`: `http://`, or `https://` with ordinary CA-verified TLS, e.g. behind a reverse proxy — both dialed exactly as before) or mTLS (`https://` canonical `host:port` URL plus the `Pin` learned from the invite); `Registry.Transport()` is the one transport every peer-bound request must use (catalog pulls, notify, heartbeat, proxy, sync trigger). Redeeming an invite from a node that's already a legacy peer with the same name upgrades that peer in place — same id, same mirror and cursor, same `.strm` paths. DB is the source of truth after first boot (peers added via the dashboard persist even if never in the `PEERS` env var). A dashboard-added peer's registry id is derived from the `node_id` its `/health` reports (`peers.idFor`: slugged to `[a-z0-9_-]`, `_01`, `_02`… on collision, `local`/`unknown` reserved, UUID only if it reports no name); it's assigned once and never follows later renames, since it names the peer's `.strm` folder. Builds before this assigned UUIDs; `migrateUUIDIDs` renames those on boot across every peer-id column, and the next `Reconcile` moves their files. Each peer gets its own heartbeat goroutine (`GET /health`, ~15s + jitter) driving `ONLINE → DEGRADED → OFFLINE`; `Sync` only fetches catalogs from `ONLINE` peers. `Peer.LastSeen` (`last_seen_at`) drives `Offering`; when a heartbeat flips it (grace expired, or the peer is back), `OnOfferingChange` queues a pull-only sync (reason `peer-state`) so items are withdrawn or restored right away rather than at the next scheduled sync. Every probe (add-peer handshake and heartbeat) also reads the `version` field off that peer's `/health` response and caches it on the `Peer`, so `GET /api/v1/peers` can show what jellysync build each peer is running — best-effort only, an older peer without the field just reports an empty version. Each heartbeat also resolves the peer URL's host to an IP (`Peer.IP`, not persisted), shown on the dashboard and used as a fallback by `ResolveCaller`.

**internal/proxy** — streams playback bytes, never exposes an API key off its own host. `GET /api/v1/proxy/stream/{peerID}/{itemID}`: `peerID=local` serves directly from this node's own Jellyfin using its own key (this is what a *peer's* jellysync calls on our behalf, and the only form the peer port routes — a client can't use us as a relay); any other `peerID` forwards the request to that peer's own node at `.../stream/local/{itemID}`. A node's own Jellyfin key never leaves its own host, and this node never talks to a peer's Jellyfin directly. Outgoing (`local`) traffic is attributed to the authenticated `Caller` on the peer port; on the legacy port via `ResolveCaller`: the caller's `X-Jellysync-Peer` header is its own `NODE_ID`, i.e. our peer's *Name*, not the id we assigned it, so it must be mapped back to the registry id (falling back to source IP) — otherwise one peer's traffic splits across two keys. `/api/v1/traffic` and `/metrics` also fold totals persisted under a peer's name by older builds into its id. `DELETE /api/v1/traffic` (the dashboard's Traffic "clear" button) zeroes every peer's totals and history, in memory and in `peer_traffic`.

**internal/webui** — `go:embed` of `static/`, the built Svelte dashboard (`web/`). Talks to the `/api/v1/*` endpoints above.

## Logging

Everything logs through `log/slog` (text handler, `key=value` attributes), configured once in `main.go` from `LOG_LEVEL` (`internal/logging`, default DEBUG). Conventions: errors go in an `err` attribute (`logging.Err(err)`), durations are rounded to ms. INFO is one summary line per sync step (`sync started`/`sync finished` carry a `reason`: startup, scheduled, manual, peer-notify), plus peer state changes, notifications and config changes; DEBUG is per page/file/stream detail; WARN is anything degraded that the node recovers from (a failed peer pull, an unreachable peer); ERROR is a failed step. `catalog.Sync` and `strm.Reconcile` return stats structs (`SyncStats`, `strm.Stats`) that `syncrun.RunLocal` turns into its summary lines. Don't add per-heartbeat or per-dashboard-poll logs above DEBUG.

## Security model

Two ports, two trust levels:

- **Peer port `:8443`** (published as `8498` in `docker-compose.yml`) — the public one, open only with `MTLS_PEERS=true`. Mutual TLS with pinned keys (`internal/peerauth`): only clients (nodes that redeemed one of our invites), peers (nodes whose invite we redeemed) and pending invite keys complete the handshake, and each route is limited to the caller kind that needs it. A client may read the catalog/feed, stream `local` items, read our own (`local`) sync status and trigger a local refresh (rate-limited per client); only a peer may notify us; only an invite key may pair. Nothing else — the dashboard and its API included — is routed there. Any new peer-facing endpoint must be added to `app.peerMux` deliberately, behind the right `peerauth.Require*`.
- **Dashboard port `:8080`** — unauthenticated, as before: the dashboard, its admin API, and (with `HTTP_PEERS`, the default) the legacy peer API used by peers added by URL. Anything that can reach it is trusted, so it must stay on a private network (LAN/VPN). The `X-Jellysync-Peer` header and source IP are only used for attribution there, never for authorization.

The node's private key is in the DB; whoever has the DB file can impersonate the node until its clients revoke it and its peers re-pair.
